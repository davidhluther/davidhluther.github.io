Governance as Code

Three sweeps before I admitted prose wasn't working

My weather site uses a pipe to separate data points on a line. Small rule, set on 2 July and swept across the site the same day. It came back. Swept again during a later feature build, and it came back again. On 17 August I swept it a third time and, in the same change, made it a rule the test suite enforces, which is the only sweep that has held.

That pattern is the whole argument. The styleguide it belongs to is a serious document with tiered rules and a quarterly re-check, and it lived as prose for months while I kept catching violations by reading the live page. A rule a human has to remember is a rule that decays at exactly the rate you stop paying attention. The linter's own docstring is blunt about the reason it exists, which is that prose-only rules demonstrably don't hold.

A draft validator can't see the copy that ships

The Corpay content engine runs a validator over drafts before they publish, which is the right place for an article pipeline. It is also structurally blind to most of the copy on a web application. Nobody drafts an aria-label. Nobody sends a nav item or a table header or an Open Graph description through editorial review.

So this one reads the artifact instead. It pulls user-facing strings out of JSX text nodes, prose string literals, metadata titles and descriptions, aria-labels, and markdown posts, which comes to 1,722 strings today, and applies the mechanically decidable subset of the styleguide to all of them. Fourteen rule codes cover colon capitalization and colon budget, em-dashes in interface copy, nav label sets that aren't uniformly title case, table cells and stat captions starting lowercase, straight quotes that JSX will never convert, banned vocabulary, the separator standard, and one bug class worth naming on its own.

That one is JSX_SPACING. A JSX text node carrying an HTML entity that also wraps across source lines silently loses its leading space when it builds, so "range is scored" ships as "rangeis scored." The source looks correct, review catches nothing, and the defect exists only in the production bundle. It is precisely the class of error that a draft-stage check cannot reach and a human proofreader will read straight past, because they are reading the source rather than the output.

The first run found 156 violations in a tree that had passed months of my own review.

Severity is the design decision, not the rule list

Every rule ships with a severity, and the split is deliberate. Errors are the unambiguous mechanical cases, meaning a lowercase complete sentence after a colon, a straight quote in rendered JSX, a nav set that mixes cases. Warnings are every judgment call, including the colon budget and any lowercase-after-colon that might be a legitimate fragment or enumeration.

The reasoning is recorded in the source, and it is the part I would keep if I could keep only one line: a linter that forces bad rewrites gets switched off. A tool that fails your build over a defensible sentence teaches you to disable the tool, and then you have neither the rule nor the tool. Running it against the live tree right now returns zero errors and 69 warnings. The gate is clean and the advice is still there, unread until someone wants it, blocking nothing.

The gate itself is one pytest case that lints the real source tree and asserts no errors, so a copy violation fails the suite exactly like a broken function would. A companion test asserts the opposite boundary, which is that unapproved drafts are never linted. Shipped copy is governed; work in progress is left alone.

The word lists are deliberately not mine

Banned vocabulary is not defined in this linter. It reads the canonical JSON that the shared article validator reads, and if that file is missing it exits loudly rather than falling back to a built-in list.

# Canonical, shared word lists. Forking a copy into this repo is banned by
# ~/Projects/CLAUDE.md, so we read the shared file and fail loudly if it moved.

A test pins the filename and asserts that real terms resolve through it. This is a rule I hold across every project because I have already been bitten: a sibling brand's forked validator drifted silently, and nobody noticed until the two brands were enforcing different standards while believing they shared one. A loud failure on a missing shared file is better than a quiet success on a stale local copy.

The second rule was a limit I couldn't see

The other standard is infrastructural, and it earned its gate the expensive way. Every deployment failed from 6 to 16 August because the hosting plan refuses more than twelve serverless functions per deployment, and it refuses at a step that runs after the build reports "Build Completed." So the build stayed green, the scheduled jobs stayed green, the data pipeline kept committing daily, and production quietly served a ten-day-old build. Nothing anywhere was red.

The fix is a pull-request check with two jobs, and the reason there are two is worth more than the check itself. A static model reads the route tree and predicts the count in about a second, needs no toolchain, and gates every relevant pull request. A ground-truth job runs a real platform build and counts the function bundles the builder actually emitted, which is slower, exact, and the arbiter whenever the two disagree. When they diverge, the workflow warns that the measurement wins and the model needs updating, rather than quietly trusting the fast answer.

Two smaller choices in there matter more than they look. The budget fails at ten rather than twelve, so a model that under-counts by one still trips the check before a real deployment does. And a build that fails because the platform CLI wanted credentials posts a notice naming the exact owner step instead of going red, because a credentials failure is not a signal about the function count and must not read as one. A check that cries wolf gets ignored on the day it is right.

A standard that cannot fail a build is a preference, and preferences lose to deadlines.

Why this matters for AEO

"How do you hold editorial standards across hundreds of pages" is a real interview question with a bad common answer, which is a style guide, a review step, and hope. Answer engines extract from the rendered page, so the copy that determines how you get quoted is exactly the copy no draft process ever sees: the metadata, the headings, the nav labels, the table cells. Governing drafts and leaving the artifact ungoverned means governing the half that doesn't ship.

The transferable pattern is smaller than either tool. Write the rule as prose first, because you need to understand it before you can encode it. Then watch which rules keep getting violated, because those are the ones that will never hold on attention alone, and compile only those into something that blocks. Grade the mechanical cases as errors and everything arguable as advice, or the team will route around the whole apparatus within a month. And point every instance at one canonical definition, so that having the rule in two places doesn't quietly become having two rules.

What I don't have is evidence that the warnings ever get read. Sixty-nine of them are sitting in that output right now and I look at them roughly never, which suggests the honest split might be narrower than the one I built.

Build notes. Both gates are public in the repo, as scripts/copy_lint.py and the function-budget workflow, with their reasoning in the comments rather than in a wiki. 66 of the project's 581 Python tests exist to keep the two gates honest. The copy linter was generalized into my shared cross-project library the same day it shipped. The two gates themselves are copy_lint.py and function_budget.yml, readable end to end.
