What it is

A retrieval-augmented generation system I designed and built solo over a private corpus of licensed lecture video and slides: ingestion, chunking, embedding, storage, retrieval, and LLM answer synthesis with enforced inline citations. The corpus content is copyrighted, which shaped the architecture in a useful way. The retrieval layer is explicitly the privacy and IP enforcement boundary: it surfaces passages for synthesis and citation, and never republishes them.

The ingestion pipeline

Six idempotent stages, each rerunnable without damage:

  1. Transcripts: parse VTT/SRT/text, clean, and segment, keeping timestamps.
  2. Visuals: scene detection on the video (PySceneDetect), one frame per scene, perceptual-hash dedup so the same slide shown for ten minutes becomes one image.
  3. OCR and captioning: Tesseract for slide text, with an optional Claude-generated caption for diagrams. Dedup upstream means captioning runs once per unique slide, not once per frame.
  4. Chunking: ~400-token sliding windows over transcript segments with a 60-token overlap tail carried into the next window; one chunk per unique slide.
  5. Embedding: batched calls to voyage-3-large (1,024 dimensions), behind a cost gate.
  6. Storage: Postgres with pgvector on Supabase, or a local JSONL store for offline development.

A manifest tracks per-lecture content hashes, so reruns reprocess only what changed. That's what made it practical to process 60+ lectures incrementally across working sessions instead of in one heroic batch job.

Retrieval: one SQL function, citation-first

All retrieval flows through a single PL/pgSQL function against an HNSW index. It takes a query embedding, a result count, and a JSONB metadata filter for scoping:

create or replace function match_chunks(
  query_embedding vector(1024),
  match_count int default 8,
  filter jsonb default '{}'::jsonb
)
returns table (
  id uuid, lecture_id uuid, source_type text,
  start_ms bigint, text text, metadata jsonb, similarity float
)
language sql stable
as $$
  select c.id, c.lecture_id, c.source_type, c.start_ms, c.text, c.metadata,
    1 - (c.embedding <=> query_embedding) as similarity
  from chunks c
  where c.metadata @> filter
  order by c.embedding <=> query_embedding
  limit match_count;
$$;

Every chunk carries its source timestamp (start_ms) and course/lecture metadata, so retrieval always answers "where did this come from." A later migration joined lecture and course titles directly into the function's return shape, so citations need no client-side joins. Answer synthesis is required to cite inline; an answer that can't point at its passages doesn't ship.

Engineering decisions worth stealing

  • Cost caps before spend. The embedding stage projects run cost from token counts and refuses to start a run that would exceed the configured cap. Failing before spending beats failing mid-run.
  • Provider abstraction with provenance. The embedding provider is one config line (Voyage, OpenAI, or local Ollama), and every stored vector records which model produced it, so a future provider switch is an unambiguous re-embed rather than an archaeology project.
  • Public code, private data. The pipeline, schema, and docs are structured for a public repo; transcripts, images, and embeddings live outside it, enforced by redundant gitignores and a private database project. Confidentiality as architecture, not as policy.
  • Offline fallback. The same cached embeddings power a fully offline hybrid search engine when the network path isn't available.
