What it is

A retrieval-augmented generation system I designed and built solo over a private corpus of licensed lecture video and slides. Ingestion, chunking, embedding, storage, retrieval, and LLM answer synthesis with enforced inline citations. The corpus content is copyrighted, which shaped the architecture in a useful way. The retrieval layer is the IP enforcement boundary, surfacing passages for synthesis and citation without ever republishing them.

The ingestion pipeline

Scene detection deserves a word. A slide shown for ten minutes of video becomes one frame after perceptual-hash dedup, and the optional Claude caption for diagrams runs once per unique slide instead of once per frame. Tesseract handles the plain slide text. Cheap, boring, and it cut the captioning bill by an order of magnitude.

The manifest is what made the project survivable. Hundreds of lectures got processed incrementally across working sessions, and a rerun after any failure reprocessed only the lectures whose content hashes changed.

Retrieval, citation-first

All retrieval flows through a single hand-written SQL function (declared language sql stable) against an HNSW index. It takes a query embedding, a result count, and a JSONB metadata filter for scoping.

create or replace function match_chunks(
  query_embedding vector(1024),
  match_count int default 8,
  filter jsonb default '{}'::jsonb
)
returns table (
  id uuid, lecture_id uuid, source_type text,
  start_ms bigint, text text, metadata jsonb, similarity float
)
language sql stable
as $$
  select c.id, c.lecture_id, c.source_type, c.start_ms, c.text, c.metadata,
    1 - (c.embedding <=> query_embedding) as similarity
  from chunks c
  where c.metadata @> filter
  order by c.embedding <=> query_embedding
  limit match_count;
$$;

Every chunk carries its source timestamp and course metadata, so retrieval always answers "where did this come from." A later migration joined lecture and course titles directly into the function's return shape, killing the client-side joins citations used to need. Answer synthesis is required to cite inline. An answer that can't point at its passages doesn't ship.

This is the machinery answer engines run on: chunking, embedding, retrieval, synthesis, citation.

Decisions worth stealing

The embedding stage projects run cost from token counts and refuses to start a run that would exceed the configured cap. Failing before spending beats failing mid-run, and the cap has caught two runs that would have been expensive mistakes.

The embedding provider is one config line (Voyage, OpenAI, or local Ollama), and every stored vector records which model produced it. A future provider switch becomes an unambiguous re-embed instead of an archaeology project. Voyage won on retrieval quality and on a deployment quirk, since it's callable identically from Python during ingest and from a serverless function at query time, where a local Ollama can't be reached.

The pipeline, schema, and docs are structured for a public repo while transcripts, images, and embeddings live outside it, enforced by redundant gitignores and a private database project. Confidentiality as architecture rather than policy. The same cached embeddings also power a fully offline hybrid search engine for when the network path isn't there.

Why this matters for AEO

Having built each stage myself, I can reason concretely about why an AI assistant cites one page over another, what makes content chunk-friendly and citation-worthy, and where retrieval actually breaks. If you want to know what a 400-token window with a 60-token overlap does to your carefully crafted page intro, I can tell you exactly, because I've watched it happen to 23,615 chunks of someone else's prose.

Build notes. Designed and built by me alone, with Claude Code as the engineering team. Python, Tesseract, and Postgres/pgvector on a managed database's free tier. Embedding is the only real spend, and every run is gated by a hard pre-run cost cap.
