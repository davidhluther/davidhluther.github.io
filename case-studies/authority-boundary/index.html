The Authority Boundary

For five monthly cycles I have run the records system for a nonprofit board I serve on. It gathers the inputs, assembles the read-ahead packet, turns the meeting recording into minutes, and keeps the archive. Generating documents was the easy half. The hard half was deciding, structurally, which document wins when two of them disagree.

The pipeline stops on purpose

A cycle runs across three APIs. Mail supplies the reports that arrive as attachments, drive holds the archive, and the conferencing platform holds the recording. Everything that gathers runs on read-scoped credentials. The one stage that composes runs on a credential of its own, which matters more than it sounds.

Minutes come out of the recording through transcription and then a generator that writes the document from code, so the required sections exist because the code emits them rather than because somebody remembered. Assembly works the same way. Files convert to one format, blank pages come out, order is fixed, and any expected input that never arrived gets flagged in the output rather than quietly dropped. The dangerous failure of a document assembler is a packet that looks complete.

The last stage composes the outbound message to the board and stops. A person sends it. The compose credential is scoped so the system cannot send even if I told it to, which makes approval a property of the architecture rather than a habit. Habits erode under deadline. A permission that was never granted does not.

One build step surprises people. Every artifact's sharing state gets re-verified against its intended audience each cycle instead of being inherited from the cycle before, because updating a file in place preserves whatever permission it already carried. A document can be perfectly correct and quietly readable by the wrong audience, and nothing inside it will tell you.

Underneath sit those eight scripts and four task-scoped skills I invoke by name, each usable alone or as part of the full cycle, because some months need only one piece.

The tracker was stale, and I believed it

The rule that governs all of this came out of my own mistake.

A tracker in my working files listed an item as an opportunity still open. The source record showed it had been secured and already spent. Nothing was invented and no model hallucinated anything. The tracker was simply old, and I trusted it because it was the convenient artifact rather than the authoritative one. It answered in two seconds. The document that actually knew sat a folder tree away, unindexed.

Every instinct after a miss like that says fix the prompt. The prompt was fine. My system had offered a fast wrong answer alongside a slow right one, and then acted surprised when speed won.

Two trees, one rule

Documents that other parties produced live in one tree. Anything I built by inference lives in another. The split is structural rather than editorial, so "where did this come from" gets answered by the path before anyone reads a word.

The rule is written into the operating instructions every session reads. Where a derived tracker disagrees with a source document, the source wins, and no claim gets asserted without opening the source. It is short enough to hold in your head, which is most of why it works.

Summaries stay lossy on purpose

Minutes are a lossy compression of a meeting, and mine are deliberately not backfilled. When a digest surfaces something the minutes left out, the minutes stay as they are. They carry what their own genre requires and nothing else.

This runs against a strong instinct. Material in the source that the summary missed feels like a defect, and enriching the summary feels like the repair. Do that for a year and the summary becomes the document everyone cites, the source stops being opened, and the compression that made the summary useful now hides whatever it dropped. A summary trusted completely is a summary nobody checks.

The retrieval layer that makes lossiness safe

Lossy summaries are only safe when the source is genuinely reachable, so the archive carries 17 banked source transcripts, 15 per-meeting digests written against them, and 11 secondary in-meeting chat logs, indexed so a session hunting an answer lands on the authoritative document ahead of my summary of it.

The digests are the piece I would rebuild anywhere. Each carries an explicit section listing what is present in the source and absent from the summary, which is a map of the compression loss written while both documents were open.

The design target was cost. A rule that makes the correct answer expensive holds only until the first week you are in a hurry, so making the source as cheap to reach as the summary is what lets it survive a deadline.

The interesting problem in a document system is not generation. It is knowing which document is allowed to be believed.

Why this matters for AEO

All of it is the problem answer engines have, at a different scale. A model assembling an answer chooses between a convenient artifact and an authoritative one, and it makes that choice at retrieval time, from whatever the index puts in front of it. Most grounding failures come from a stale derivative winning a race against its own source rather than from anything invented, which is exactly what my tracker did to me.

The transferable parts are the boring ones. Mark which documents in a corpus are allowed to be believed. Refuse to let summaries grow until they replace what they summarize. Build retrieval so the primary document is the cheap one to reach. Citation integrity in an AI answer and provenance discipline in a filing system are the same problem, and neither gets solved by better prompting.

The honest limit is that my authority rule is a sentence rather than a check. Nothing stops a future me from filing a source in the wrong tree, and the system would never know. The gates I built on another project exist because a rule that lives only in prose eventually stops holding, and by that standard this one is on borrowed time. I have not written that check yet.
