How work passes from one stage to the next

Most recurring analysis programs re-buy the same expensive data every cycle, can't compare this month's output to last month's, and can't trace a number in a leadership deck to the API response behind it. One habit fixes all three. Every stage writes to a dated file saying what it is and when it was pulled, and the next stage reads it instead of calling the API again.

Exactly four written rules cover the handoffs, each binding a pair of roles like a process doc binds two teams. The collector hands the analyst one snapshot of the raw data per cycle, so two analyses of a month can't disagree. Staleness is the gatekeeper's call, and it tells the analyst what to re-pull and what to read off disk. The synthesizer, which turns those numbers into the story, may only read, never call an API. A skill that learns something mid-run can only propose a note for an orchestrator to merge at a checkpoint.

The gatekeeper runs on one number. One value in one config file sets the base cadence, and each analysis carries a multiplier against it, so fast-moving work goes stale in days and structural work stays good for months. Change that number and every deadline moves with it, in proportion.

So a "full" audit is usually a partial re-pull. Stale pieces get bought again, the rest comes off disk, and cost control ends up a property of the design rather than of my discipline. Nothing gets overwritten, so any two cycles can be compared, and somebody new can read the data flow off the folder names.

One engine, many brands

The analysis layer is 34 skills, none with a brand name inside it. Each takes a brand as an input and looks it up in a registry of profiles, the only place I look to answer a governance question. A profile lists the markets and the vendor reports behind them. The rest sets which markets I trust, the competitor set, the refresh cadence per analysis, and how the brand's naming maps onto standard fields.

Onboarding a brand means filling one out against a written checklist. Nobody copies code. I wrote the case against forking the skills per brand after a sibling brand's forked validator drifted unnoticed. A fix for one brand now reaches all of them on the next run, which isn't a promise anyone keeps. It's how the files are wired.

The line between employer work and my own is wired the same way. Brands outside the employer never touch data the employer pays for. What crosses is method alone, meaning a skill, a rubric, or a schema. The battery suite I run for my consultancy is that portability in practice, the same method rebuilt for far fewer prompts in one local market.

What a finding has to survive before it ships

Nothing reaches a client or executive without passing an evidence gate. Findings get one of four labels, from confirmed at the top down through likely and unverified to hypothesis. A hypothesis can't become an action item, only a queue entry to investigate. A causal claim faces four more tests: timing, size of effect, whether anything else explains it, and a mechanism I can describe step by step.

Borrowed statistics get a second grade. Confidence grades my finding, and an A through D tier grades the study behind the number, assigned by reading the original rather than a summary. A finding marked confirmed on a D-tier statistic isn't confirmed, and vendor-funded research about the vendor's own category caps at mid-tier however clean the method. The evidence pipeline, drift measurement and retraction tables included, has its own case study.

A shared notebook carries what gets learned mid-cycle. A source that turns out richer than expected, or two audits that contradict, gets a short entry saying what kind of finding it is, how sure I am, and which analysis picks it up next run. The two sides are lopsided on purpose. Skills only read. Writing takes a command-line tool that checks the entry's shape, run by a person, so no unreviewed run can poison the shared memory.

Every number in here can say where it came from, and one that can't doesn't go in the deck.

The system catches its own operator

The checking here is built to argue with me. Before one leadership deliverable went out, an agent knocked down three of my own cause-and-effect claims, and what shipped was what survived. A detection script got thrown out on the same principle. Run against a case where the right answer was nothing, it reported something anyway, so its "confirmed" finding was the instrument hearing its own echo.

When an executive pushed back on a zero in a chart, the re-pull showed it came from a query limit, not a real absence, and that became a standing class of correction I check for every time instead of a one-off apology. A tool is assumed wrong until it passes a control, and a skeptical question from leadership is a free test case.

The same suspicion covers anything that reports itself finished. A pipeline once marked its work complete on the tracking board when the files it was meant to produce didn't exist. So the rule is short. A completion report is a claim, the files at the end of the chain are the evidence, and every dispatched batch clears that check first. The best day here ran seventeen packages that way, each leaving a readable pull request, with none failing.

Every run has to say what it cost

The vendor data this runs on is sold in units, and I treat units like cash. Before any large pull the pipeline checks the balance, every file records the units that step burned, and every run ends with a mandatory cost report, calls per endpoint times the published cost per row. An expensive habit shows up on the run that introduced it, not six weeks later on the invoice.

One written-down lesson is my own. I fanned several briefs out in parallel, exhausted the unit ceiling, and the two fixes sit in the file beside the mistake. The pipeline signs in with the metered account rather than my subscription login, on purpose, so I can tell its spend from mine.

The reports leadership sees

A program that can't be explained upward dies, so the reporting got the same engineering as the data. The weekly leadership dashboard pulls each source on its own, and week-over-week changes come from a stored copy of last week rather than a recalculation, so an outage can't manufacture a change that never happened. One set of numbers renders three ways, a spreadsheet for analysts, a live app for looking things up, and a flat file that survives a paste into a slide.

Every tile in the app is a record carrying its label and unit, its basis, its source, and any caveats. A missing value renders as "n/a, see note" and never as a zero. Before the verified data underneath existed, the app ran on obviously fake sample data, watermarked from a flag in the data file, so nothing real-looking could ship early.

I present the program to leadership as capabilities the company now has instead of things I did, mapped onto priorities the marketing organization already wrote down. The bridge was a problem the executives already felt. Paid demand generation is push, where you buy attention and past a point more money buys less, while discovery inside an AI answer is pull, where buyers come asking and old work still pays. Every time that argument appears in my own material it's labeled a strategic argument, not something proven. That's the evidence rule turned on my own advocacy, the hardest place to apply it.

Handing work to agents, in writing

This engine is one workstream inside the bigger setup I run for everything else, which Six Domains, One Operating System covers. Here, a session working from a written charter dispatches work to one session per lane, for strategy and intelligence, content production, the platform, measurement, and bringing new brands on.

A handoff is a written brief dropped into the repository where the work happens, written as though the receiving session has never heard of me. It reads like a work order: the mission, the rules in priority order, the environment facts I've checked and marked so nobody re-checks them, the data shape it should hand back, and how to land the work.

Which model does what is policy, the expensive one held for judgment and mechanical work sent down a tier. The charter names how this setup most likely fails, the dispatcher dropping a level to do the work itself and wrecking its context, in there because it happened once.

The method is written up as a kit somebody else could pick up: a rebuild guide, a data-flow map annotated at every hop, a walkthrough of one real cycle, and an empty folder tree with templated configs. A team I've never met could stand it up. Same instinct behind the education hub I built inside the company, a plain-language layer for the wider marketing organization where every page names its source and last-checked date, the repository stays the master copy, and numbers that haven't passed evidence review don't appear. My note in the planning doc says the point was so not everything is held in my head.

What a senior AEO role gets from this

It adds up to channel ownership that survives an audit. Measurement produces numbers I can defend, the content engine produces pages that get cited, and this layer makes both repeatable, portable to a new brand, costed on every run, and explainable to a CEO. One person ran it all with Claude Code as the engineering staff, which I'd argue is the shape senior AEO work has now. What I don't know is which gates hold with a team instead of one person, and which stop being a rule and become somebody's job.

Build notes. Built at Corpay by me, hands on keyboard, with Claude Code as the staff. Python, GitHub Actions, and vendor APIs metered behind hard gates. The specific performance numbers live in my resume; every mechanism above is described exactly as it runs.
