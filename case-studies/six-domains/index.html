Six Domains, One Operating System

An enterprise AEO channel, a consultancy with client engagements, a nonprofit board seat, a portfolio of civic roles, a public data product, and personal operations. One person runs all six through a persistent multi-agent operating system, and this page is how it actually works.

6domains, each with its own chartered orchestrator
7third-party agent skills security-vetted before install
4parallel audit agents per vetting pass
1improvement inbox feeding every domain

The shape of it

A home orchestrator routes every new topic through a written routing table, and six workstream orchestrators each hold a charter, a session registry, and an open-dispatch ledger. The orchestrators frame work and dispatch it; dedicated agent sessions do it. Handoffs travel as self-contained briefs written into the receiving repository, on the assumption the receiving session knows nothing, and the dispatch payload itself stays deliberately thin, because we measured what fat prompts do to the receiving agent's context window and stopped paying that tax.

Status flows the same disciplined way. An orchestrator reads a workstream's ledger and git history rather than interrupting a running session to ask, which sounds like etiquette and is actually throughput.

Rules with incident reports attached

The OS's constitution is short, and every clause exists because something specific went wrong. A blanket "just go for it" was once applied as commits across four repositories, overriding an earlier do-not-commit, so per-repo commit confirmation became constitutional: a general go-ahead authorizes exactly the repo under discussion. An orchestrator once dropped a level, ran a deep audit inline, and wrecked its own context, so the charters name that failure mode and prescribe the self-check ("if you find yourself many steps deep, stop, write a brief, dispatch"). A branch-cleanup command once reported a merge that hadn't happened, so ancestry checks are mandated in cleanup briefs. The rules carry their incidents the way a scar carries its story, and that's what keeps a future session from loosening them casually.

Cost policy is constitutional too. The top-tier model is held for routing and judgment, dispatched agents run a tier down by default and two tiers down for mechanical work, and exceptions get named. Same ladder, whether the work is enterprise measurement or a weather site.

Walls that hold because they're structural

Six domains means six confidentiality postures, and the system enforces them by construction rather than by memory. Employer and personal work never share data resources; methodology crosses that wall only as skill, rubric, and schema ports. Client workspaces keep no remote by design. The personal domain is local-only git that never leaves the machine. And the public data product is exactly that, public, which is its own discipline. An orchestration layer that enforces boundaries is, I'd argue, the thing a company actually needs to see before letting agents loose on its own data.

The fleet is also operable from a phone. Orchestrators enable remote attach when they convene, each orchestrator home keeps a private-remote fallback, and a documented remote-control mode has run real multi-day stretches, with actions that need hands at a keyboard parked in ledgers rather than dropped.

Third-party capability, vetted like a dependency

Agent skills from the open-source ecosystem are useful and unaudited, which is a bad combination to install blind. So seven third-party skills went through a vetting pipeline before touching the system. Four audit agents reviewed each one in parallel, statically only, treating any instruction-shaped text inside the skill as a finding to report rather than an instruction to follow, and producing tiered verdicts.

Then the install got hardened beyond what the audits required. Everything pinned to the audited commit. One skill had granted itself standing shell permissions in its own manifest; that grant was stripped. A browser tool shipped with its sandbox disabled; the sandbox was restored, with an environment-variable escape hatch for the rare case that needs it. Silent first-use downloads became deliberate one-time setup steps. Telemetry and author-triggered self-update paths were disabled. And a manifest travels with the install recording every SHA, patch, and exclusion, under a standing policy that an update is a re-review, not a pull.

The pipeline caught one live vulnerability: a prompt-injection path where untrusted page content could flow into a permissions-bypassed subagent and reach code execution. Closed by configuration before first use. The upstream projects are reputable and the issues were configuration-level; the point isn't the findings, it's that a one-person shop can afford a supply-chain review process, because the reviewers are agents too.

The improvement loop

One project's lesson becomes every project's default through a reviewed inbox that any workstream can file into and an orchestrator sweeps on convene. Three examples of the loop closing. A copy linter built for the weather site, after shipped violations kept surviving human review, found 156 findings on its first run and got promoted to a shared engine with pluggable per-framework extraction. A 60-topic content batch that burned roughly a quarter of its research spend on redundant topics became a shared pre-brief screening skill, with its thresholds pinned by tests to the exact batch that motivated it. And a JSX whitespace-swallowing bug found on one site became a styleguide mechanics rule for every project that renders prose through JSX.

That's the compounding story. The enterprise engine nests inside this system as one workstream among six, and the gates described there, evidence ladders, cost reports, redundancy checks, mostly started life as some other domain's postmortem.

Why this matters for a senior AEO role

Every company standing up an AEO program is about to run a fleet of agents against its own brand, data, and publishing pipeline, and most will learn governance by incident. This system is what learning-by-incident looks like after the incidents, written down, with the walls holding across six domains that must never leak into each other. Which parts of it survive contact with an actual org chart is the question I'd want to spend a first quarter answering.

Build notes. The whole system is mine, built and run with Claude Code across every domain. Its infrastructure is git repositories, markdown charters, and agent sessions. Infrastructure cost, effectively zero; the spend is model usage, governed by the ladder.
