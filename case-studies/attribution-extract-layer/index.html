The Attribution Layer That Can't Write Back

Web analytics ends at the click. In my day job the questions that matter start after it, when a visitor becomes a lead and a lead becomes pipeline. Answering them meant building an extract layer over the marketing-automation system, and the design constraint I cared about most is that the layer is incapable of changing anything it touches.

The funnel goes dark at the form

The measurement program documented in the AI-visibility study could see impressions, citations, clicks, sessions, and on-page behavior. Everything upstream of the form fill, nothing downstream of it. So content got valued in sessions, and the one channel-level fact worth acting on, that AI-referral traffic converts at the top of the channel table, stopped at the channel. Which piece of content produced which lead, and what that lead turned into, lived on the other side of a wall.

The other side of the wall is Marketo, and Marketo knows things web analytics structurally can't. Its Munchkin tracker follows anonymous visitors the same way any analytics tag does, but the moment one of them fills out a form, the platform binds that visitor's accumulated history to the new lead record. Months of pre-conversion behavior, attached retroactively at the instant identity appears. It also carries the per-lead source and UTM fields, the lifecycle stages, and the join keys into the CRM where pipeline lives. An extract layer over that system is the missing half of the funnel.

A client that refuses to write

Anything that authenticates against a production marketing database deserves suspicion, so the client is read-only by construction rather than by policy. It will send a POST for one purpose only, controlling bulk-export jobs, and refuses any other write-shaped request in code. It refreshes tokens on the expiry error codes, backs off on rate limits, and carries a soft abort at 10,000 API calls per run so a bug loops into a ceiling instead of into the instance's daily quota.

On top of that client sit three jobs. A daily incremental pull walks thirteen activity streams in four groups, web, lifecycle, email, and data-value changes, each behind its own watermark, plus roughly fifty fields for every new form-filler. A backfill pulls the full year of history through the Bulk Activity Extract API, month-chunked and checkpointed after every chunk, because the platform allows 500 MB of export a day and a full year does not fit in one allowance. When the allowance runs out, the checkpoint file knows where to resume tomorrow. Hundreds of thousands of events have landed so far and the backfill is still walking, which is the honest status of any job built to survive interruption. The third job snapshots the asset inventory, programs, campaigns, forms, and lists, since activity rows reference everything by id and an id without its name is trivia.

Every run of every job appends one outcome row to a log, success or failure, no exceptions. A pull that silently didn't happen is worse than one that failed loudly, because the gap looks like a quiet day in the data.

Scrubbing at three points, because the API leaks at three

The platform offers up personal data through three separate routes, so one filter is two short. A field allowlist handles the obvious route, the requested field list, keeping firmographics, lifecycle, scores, and source fields while excluding email, phone, names, and street addresses absolutely. The second route is sneakier. Change Data Value activity rows carry the changed field's new contents in an attribute, which means a lead's email address can arrive inside an activity stream that never asked for it, and a row-level filter drops those rows by the field they changed. The third route is every remaining string, covered by a final redaction pass over everything retained. The boundary past the layer is harder still. Nothing leaves it toward the web-analytics warehouse at person-level granularity, aggregate figures only.

Two ways the API lied

Both failure modes cost real diagnostic time and both are the kind you only learn against production. First, the documented option of passing the access token as a query parameter fails on this instance with error 603, which the docs describe as an access-denied condition. It reads exactly like a permissions problem with the service account, and the actual fix is transport, the token has to travel as a Bearer header. Second, two of the asset endpoints return a nextPageToken but omit the moreResult flag that the activity endpoints use, so a paginator keyed on that flag stops silently after page one. The campaign list came back thirty times smaller than reality and nothing looked wrong. The lesson that generalizes is that pagination is a per-endpoint contract, not a per-API one, and every collection pull now sanity-checks its count against a second source.

What the joins are for

The layer exists to make four cuts possible. Per-lead source attribution instead of channel-level. Multi-touch journeys assembled backward from the conversion, using that retroactively bound anonymous history. Content valued in pipeline terms rather than sessions, through the CRM join keys. And the cut I want most, AI-search traffic followed all the way to revenue, which very few B2B teams can produce because it needs every link in this chain at once.

None of those is a result yet, and this page is not going to pretend otherwise. The layer moves data. A separate validation pass is grading what the joins actually prove as I write this, and the claims here will grow only as fast as that grading allows, which is the same rule the evidence pipeline applies to everyone else's numbers. Infrastructure earns the right to a claim; it isn't one.

A pipeline that can't write back is a pipeline you can point at production.
