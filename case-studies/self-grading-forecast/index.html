A Traffic Forecast Model That Grades Its Own Homework

The site around it

Dave's Sweater is my satirical local-weather site for Boone, NC, and the public face of an idea I keep applying elsewhere. Forecasts should be accountable. The site's Right Ray / Wrong Ray tracker scores real forecast providers against verified actuals on a 100-point rubric, month after month, in public, and that rubric has its own case study, because rebuilding it four times without rigging it was the harder engineering problem. Its consensus forecast ships through a public API and an embeddable widget that loads no analytics, licensed CC BY 4.0. The traffic model extends the accountability discipline to a domain with no ground-truth provider to borrow.

What the model actually eats

"Three factors and a clamp" describes the formula, and it undersells the system. Each factor is fed by its own data family, each with its own capture pipeline, freshness rules, and documented provenance.

The six corridors are the roads that actually govern life here. The US-321 bypass and King Street through downtown, NC-105 at the US-321 split and south at Foscoe, Valley Boulevard in Blowing Rock, and US-421 out at Deep Gap. Every sensor pin was reverse-geocoded and road-class-verified before use, under a standing rule the repo calls "no eyeballed pins." The rule exists because the first-guess pins all landed on side streets. Right math, wrong input, and the model would have learned the traffic patterns of a parking lot.

One more capture detail I'm fond of, because it's the kind that silently ruins models. The flow API defaults to km/h. The capture requests mph explicitly, a mismatch caught during live verification rather than after a season of quietly absurd baselines.

The model, kept deliberately legible

The model predicts a per-corridor congestion ratio (current speed over free-flow speed) at the four daily windows.

def predict_ratio(baseline: float, event_mult: float, weather_mult: float) -> float:
    return clamp_ratio(baseline * event_mult * weather_mult)

The baseline is the mean observed ratio for that corridor, weekday class, and window, where weekday classes separate ordinary weekdays from Fridays, Saturdays, and Sundays because a mountain tourist town has four different kinds of day. Event multipliers are declared v0 priors rather than tuned constants. A home football game costs primary corridors nearly half their flow (0.55) with spillover elsewhere (0.80), move-in and commencement weekends carry 0.65, other major town events 0.75, and the Busy-ness Index nudges tourist corridors when the town reads slammed. Outflow events like fall break run above 1.0, because an emptying town drives faster. Weather contributes 0.85 under heavy precipitation or snow. Every one of those magnitudes is a first guess the grading loop exists to correct, and they're labeled that way in the source.

Cold starts fall through an explicit chain, and every prediction records which level produced its baseline, so any number traces to its basis.

def baseline_lookup(baselines, corridor, wclass, window):
    """(value, basis) via the fallback chain:
      cell -> corridor_window -> corridor -> 1.0 (default)."""

A logistic function turns each predicted ratio into a jam probability, which is what makes honest scoring possible. A probability can be wrong by a measurable amount; a vibe can't.

The predict-then-grade loop

Grading computes an absolute ratio error and a Brier score on the jam probability.

observed_jammed = obs_ratio < tm.JAM_THRESHOLD
ae = tm.abs_error(pred_ratio, obs_ratio)
br = tm.brier(prob, observed_jammed)

The model's first graded call, for the record, was King Street's 5 p.m. window, at a jam probability of 0.79. It has been graded on every prediction since, with error broken out by corridor and condition so I can see exactly which prior is most wrong. Whether the football multiplier survives its first season intact, I genuinely don't know yet. That's the fun of it.

The machinery around the loop

Six GitHub Actions workflows run the whole site's data layer, and their division of labor is the engineering. The daily weather capture chains into the comparison run via workflow_run. The traffic capture fires on four crons at the demand windows. A freshness sentinel runs after the captures specifically to catch a silently skipped cron, because the silent-skip bug above taught the repo that green isn't the same as done. A screenshot workflow accepts an iPhone-only data source through repository_dispatch, fired by an iOS Shortcut posting to the GitHub API, which is the no-server way to get Apple Weather into a static pipeline. And a function-budget gate runs a fast static model plus a ground-truth build on every PR that touches routes, born from a ten-day outage where deploys failed after "Build Completed" and production silently served a stale build. Python throughout is standard-library only, one deliberate exception aside.

The scope decisions that mattered

Two of this project's best engineering decisions were about what not to ship. An audit of the traffic provider's terms found that committing flow snapshots and derived layers to a public, permissively licensed repo exceeded what the license allowed, so the entire dataset moved to a private companion repo mounted at CI time via a deploy key. The model keeps running and self-grading daily. The model code stayed public; the data didn't. A planned "grade the big mapping provider too" comparison lane was cut before it was built for the same class of reason, despite a workable free quota.

You predict what answer engines will surface, you check what they actually surfaced, and your credibility rests on how honestly the two are reconciled.

Why this matters for AEO

AEO is a forecasting-and-measurement discipline wearing a marketing hat, and this repo is the same muscle with the weights visible. Declared priors, graded daily, every number traceable to its basis, scope cut when the data rights aren't there. If you want to audit how I actually work, every commit is public.
