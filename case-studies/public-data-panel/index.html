A Public Data Panel With a Refusal Boundary

A monthly economic and housing panel for a mountain region, joined from 25 public series into a grid of 201 months by 176 columns. The join was the easy part. The thinking went into two places I built it to fail on purpose.

201months in the grid, January 2010 to September 2026
176columns, each carrying its own license tag
36ingest modules that never exit nonzero
13payloads the export is allowed to write

What the panel is

One row per month for a rural county and the mountains around it, January 2010 through September 2026. Twenty-five public series joined on the month key and nothing else: park visitation, highway station volumes, alcohol board sales, sales tax receipts, employment, home values, and weather. Almost all are free, so the monthly refresh costs under a dollar.

Two rules make the grid trustworthy before any model touches it. A month a source doesn't cover is omitted rather than nulled, so a missing key means no observation and never a zero. And every column carries its own provenance, including the license tag the export layer reads.

The sources complete at lags months apart. An early draft named one month at the top and let the rest ride behind it, misattributing three figures. Every figure names its own month now.

Failing closed at the front door

Thirty-six ingest modules run inside one wrapper with a single rule. On any error, log to stderr and exit 0, leaving the previous series file untouched.

That reads like swallowing errors, and the reason it isn't is what the alternatives do. A module that exits nonzero, inside a refresh running 36 in sequence, halts everything at whichever endpoint went down that morning. A half-written file gets joined into the grid by the next assemble as though it were real, which is worse, because it looks like data. Exiting 0 costs freshness and nothing else.

The cost is real. This design produces columns that quietly stop advancing, visible in the generated data dictionary and invisible in a stack trace. I traded loud failure for a grid that can't be silently wrong, a trade that only pays if somebody reads the dictionary. The rule came from my forecast project.

The door at the other end

The panel lives in a private repo that also holds licensed raw data, so there is one door out. One module writes 13 JSON files, four top level and nine series, into a directory nothing else touches.

The gate is a positive allowlist over those license tags. Three clear it. Private-hold doesn't, and neither does any tag a future schema revision invents, because an unrecognized tag is not on the list. A second check refuses a small set of series by id regardless of tag.

Attribution travels in the payload. Every series and every tile carries its own string from its source's license block, so a chart detached from its file still carries the obligation. Fifteen ship in the current build. One input comes from a commercial vendor whose terms bar redistribution, so the derived indicator publishes under a generic label and the vendor's name never enters a payload at all.

The export also prunes itself, deleting anything in its output directory it did not write, so a dropped file can't linger as a stale artifact. That has a price. A monthly narrative ships inside the artifact, and archiving past issues would need a persisted file outside the prune boundary. The rule that makes the door safe is the rule that makes the archive hard.

Weather, split in two

Weather is the cleanest case. The baseline model wants daily observations, and the best free source carries a non-commercial free tier. So the weather series became two, one feeding the model and refused at the boundary by id, the other public domain station data and the only weather that ships.

The refusal keys on the series id rather than on column names, and that is the whole point. The internal series is tagged attribution-required for in-repo bookkeeping, which clears the tag allowlist on its own, so a future file spec naming its columns would ship it. Refusing the id means no spec can.

What I didn't plan is that the unpublishable series became a test. Every run compares the two temperature anomaly columns across their overlap and logs the correlation, and anything below 0.9 means one of them broke. Data I have no right to publish validates the data I do.

A licensing rule that lives in a reviewer's memory is a rule with an expiry date nobody wrote down.

Why this matters for AEO

Publishing structured data an assistant can lift and quote is the same problem this export solves. You publish what you have the right to publish, and something other than the person shipping has to check. A Dataset declaration, a public JSON endpoint, and a JSON-LD block are payloads leaving a building, quoted by machines that never read the terms. That is the playbook's publish-the-data step with enforcement.

People forget. Whoever read the terms in March has lost them by September, and whoever ships the fourth revision never read them, so the check belongs in the code that writes the file. The same instinct runs through the records pipeline I built for a nonprofit board.

I can't tell you the boundary holds forever. A tag can be wrong at its source, and a wrong tag clears an allowlist perfectly. What I can say is that nothing has left without a rule in code that let it out. Two series are still waiting on the far side of that rule, one short a second snapshot, the other short a year of coverage.

Build notes. The panel and its export are my consultancy's own code, in a private repo with no remote, because licensed raw data lives there. Every figure was re-read from the built artifacts, including the month and column counts, the ingest directory, the export output, and the 1,182 tests, run by hand because there is no CI. No client appears here, and the vendor goes unnamed for the reason it goes unnamed in the export.
